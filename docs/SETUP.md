# Setup — the parts that need your own accounts

Everything here is configuration rather than code. The application is complete
and tested; these are the credentials and console settings it reads, plus the
things worth knowing before you change them.

Nothing below is required to run the project locally with the demo history. They
matter when you deploy it, or when you want real data in it.

---

## What is already working

| | |
|---|---|
| Web client | `https://niyantrana.agnivesh.dev` — Cloudflare Pages |
| API | `https://niyantrana-api.onrender.com/health` → `status: ok`, `database: connected` |
| Inference | `https://niyantrana-inference.onrender.com/health` → `status: ok`, `functional: true` |

`/health` on the API also reports which optional integrations are configured:

```bash
curl -s https://niyantrana-api.onrender.com/health
# {"status":"ok","database":"connected","chat_enabled":true,
#  "google_sign_in":true,"google_health":false, ...}
```

Each flag is a separate feature. `chat_enabled: false` means the assistant
returns 503 and everything else works; `google_sign_in: false` means the Google
button does not render and the password form does. A half-configured deployment
degrades one feature at a time rather than failing as a whole.

## Environment variables

### Backend — Render service `niyantrana-api`

| Variable | Required | Notes |
|---|---|---|
| `MONGO_URI` | yes | Atlas SRV string. Boot fails rather than starting with a dead database |
| `SESSION_SECRET` | yes | Generated by the blueprint. Rotating it signs everyone out |
| `CORS_ORIGIN` | yes | Exact origin of the web client, no trailing slash. A wildcard is rejected at boot because it cannot be combined with credentials |
| `TRUST_PROXY` | yes | Without it Express sees plain HTTP behind Render's TLS proxy, refuses to set a `Secure` cookie, and login returns 200 while issuing no session |
| `ML_SERVICE_URL` | yes | The **public** URL. `fromService property: host` yields a private-network name that free web services cannot resolve |
| `GEMINI_API_KEY` | optional | Without it `/api/chat` and `/api/recommend` return 503 |
| `GOOGLE_CLIENT_ID` | optional | Enables Sign in with Google |
| `GOOGLE_CLIENT_SECRET` | optional | Additionally enables the Google Health connection |
| `GOOGLE_HEALTH_REDIRECT_URI` | with the above | Must be the public API callback. It defaults to `localhost:8080` for development, and that default reaching production sends users to their own machine after consenting |

`GEMINI_MODEL` is deliberately undeclared. Leaving it unset keeps the fallback
chain active — the client tries each candidate model and caches the first that
answers — and setting it pins one model and disables that chain.

### Web client — Cloudflare Pages

| Variable | Notes |
|---|---|
| `VITE_API_BASE_URL` | The API origin. Leave unset in development so the Vite proxy makes the browser and API same-origin |
| `VITE_GOOGLE_CLIENT_ID` | The same client ID as the backend. Unset, the Google button compiles out of the bundle entirely |

Both sides are needed and they fail differently: without the client ID on Pages
there is no Google button at all, and without it on Render the button works and
the server then rejects the credential.

## Google Cloud console

One OAuth client covers both features. In the project that owns the credential:

1. **APIs & Services → Library** — enable the **Google Health API**.
2. **OAuth consent screen** — app name, support email, and links to the privacy
   policy and terms. Health scopes cannot be verified without both.
3. **Audience → Test users** — add the Google accounts allowed to connect Health
   data. Every Health scope is Restricted, so until the app passes OAuth
   verification this list is the set of people the feature works for.
4. **Credentials → OAuth client ID → Web application:**

   | Field | Value |
   |---|---|
   | Authorised JavaScript origins | `http://localhost:5173` and the deployed client origin |
   | Authorised redirect URIs | `http://localhost:8080/auth/google/health/callback` and `https://<api-host>/auth/google/health/callback` |

   The redirect URI must match byte for byte — scheme, host, port, path, no
   trailing slash.
5. **Data access** — declare the three scopes the app reads:

   ```
   https://www.googleapis.com/auth/googlehealth.activity_and_fitness.readonly
   https://www.googleapis.com/auth/googlehealth.sleep.readonly
   https://www.googleapis.com/auth/googlehealth.health_metrics_and_measurements.readonly
   ```

   An undeclared scope cannot be granted, so the connect flow fails without
   these even for test users.

### Publishing status

Keep the app **published**. In Testing mode the consent screen serves only the
test-user list for *every* scope, including basic sign-in, so a visitor who is
not on that list cannot sign in at all. Testing mode also expires refresh tokens
after seven days, which the app handles — a rejected refresh marks the
connection `needsReconnect` and the card says so — but it means a Health
connection made in Testing needs reconnecting weekly.

Published, with Health scopes unverified:

| | Behaviour |
|---|---|
| Sign in with Google | Works for everyone. `openid`/`email`/`profile` are non-sensitive |
| Connect Google Health | Shows the unverified-app screen, capped at 100 users for the project's lifetime |

### Verification, and whether it is worth it

Branding verification needs the domain verified in Search Console at the **top
private domain** level — `example.dev`, not `app.example.dev` — using the same
Google account that owns the Cloud project, plus three distinct URLs for the
home page, privacy policy and terms.

Restricted-scope verification is a separate and much larger step: it requires a
demo video and an annual **third-party security assessment**, currently around
$500–$1,200 a year with the free self-scan route withdrawn. What it buys is
strangers being able to connect *their own* health data. For a personal project
that is usually the wrong trade, and the onboarding card already explains the
limitation to anyone it affects.

## Connecting real data

### Google Health

Sign in → **Onboarding** → **Connect Google Health**. The app syncs 90 days on
return and prints a per-feature report:

```
daily steps              84 days
active minutes           84 days
sleep                    79 days
resting heart rate       84 days
heart rate variability   61 days
```

Read that report rather than assuming. A feature showing `none` means the
account has no such data or the field name differs from the candidates the
adapter knows; the report names the fields the response actually carried so the
mapping can be corrected from evidence. Nothing is ever written as zero to fill
a gap.

**The account must have a data source linked.** The API answers
`ACCOUNT_NOT_LINKED` for an account with nothing behind it, and Google's message
describes this in legacy Fitbit terms. Linking Samsung Health to Google Health
satisfies it.

### Samsung Health

Samsung Health → Settings → Download personal data, then upload the `.zip`
exactly as exported on the onboarding screen. No unzipping, no folder picking.

A 23 MB archive of 14,507 entries becomes about 2.9 MB uploaded and roughly 120
days of history. HRV is not present in the export and is reported as missing
rather than derived from stress scores, which are a different quantity.

### Anything else

`POST /api/wearable/import` takes CSV or JSON from Fitbit, Apple Health, Oura,
Withings or Google Takeout, matching ~40 column aliases.

## Optional, and worth doing

- **NFHS-5 (`dhsprogram.com`) or LASI (`g2aging.org`)** — free, short
  registration, 1–2 day approval. The models are US-calibrated; South Asians
  develop metabolic disease at lower BMI and waist thresholds, so every score is
  systematically off for the population this was built for. LASI is the stronger
  of the two because it carries HbA1c and blood-pressure biomarkers.
- **GitHub Student Developer Pack** — DigitalOcean and Azure credit, enough to
  run this always-on for a year if the cold starts become tiresome.
- **Lighthouse** against the deployed client. Nothing in the build is knowingly
  failing it, but it has not been run against a real deployment.

## Things that will bite you

**Login succeeds but the user is signed out on reload.** `TRUST_PROXY` is unset,
so Express never issued a `Secure` cookie.

**Every browser request fails CORS while curl works.** `CORS_ORIGIN` does not
match the client origin exactly.

**`redirect_uri_mismatch` at Google.** `GOOGLE_HEALTH_REDIRECT_URI` and the
Authorised redirect URI differ, often by a trailing slash. It points at the API
host, not the client.

**The consent callback returns 401.** The session cookie is not travelling
cross-site; check `TRUST_PROXY` and that the client is served over HTTPS.

**The first request of the day is slow.** Both services spin down after 15
minutes idle. The client wakes them — the landing and sign-in pages start the
container while the visitor reads, and the dashboard retries around a cold start
— so this costs about 40 seconds rather than an error.
